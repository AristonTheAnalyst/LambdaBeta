# Lambda — Workout Tracking App Architecture

Flutter workout tracker over PowerSync (local SQLite mirror ↔ Supabase). Users plan sessions, log them live, and review them afterwards. PRs are fully derived on read — there is no PR table.

## The three session surfaces

**Live session** (`lib/features/session/`) is the UX foundation; the other two mirror it through the shared card/row. `SessionScreen` is a `SlidePages` wizard of five pages indexed by `SessionViewModel.k*Page`: Home (**Sessions** since 2026-10-23 — the same logs list, headerless, its Sets tab retired and its filter bar two rows of chips: exercise · variation above workout · date, the unfiltered range reading `All time`; the header's green **+** starts) → Pre-questionnaire (feeling/notes + recap) → Training (read-only preview when idle; the template picker is the header's own selector — a pill across the title band, 44 tall, no body card, 2026-10-23) → Summary (this session + Finish) → Post-questionnaire (feeling/notes + recap, Done → Home). Pre answers are written at session creation (Training's Start); the Training page's floor bar carries a **star** opening the session ratings sheet (2026-10-22; a pencil until 2026-10-23), a second door to the same pre/post bookends, and Done on the post page writes all four fields in one `updateSessionNotes` after `endSession` stamps only `end_datetime`. Training's Cancel is a **red X** in the header (2026-10-23; a square stop glyph until then — the square read as pause, the X reads as close), behind a two-verb Keep Going / Discard dialog. Re-tapping the Session nav tab while the wizard is on screen is a **browse, not an end** (2026-10-23): `AppRouter.sessionTabReselected` bumps, the wizard flushes typed values and slides to Home, and the live session keeps running underneath; Home's header then swaps Start for a green **Resume**, which returns to Training (guarded by `browseOnSessionTabRetap` — only Training/Summary are live pages a tap can leave; the post page is a one-way door). The Training floor's date bar walks **two stacks** (2026-10-23), and the radio pair under the date switches them: **EXERCISE** (the default on both surfaces) steps the active exercise's own past performances — the card's sets swap and the page stays, the stack strictly older than today's sets and bound to the exercise it was stepped on — while **SESSION** walks whole records **in place** (2026-10-22): its left chevron steps onto the newest completed record (`previousSessionId`, read as the newest session stamped before this one's start; right stays grey — today is the top of the stack) without any route change — the page hosts the record through `SessionHistoryPeek` (the viewer's own `SessionDetailView` over a `SessionDetailViewModel` from `SessionViewModel.createRecordPeek`), so the route and wizard stay put while the record's card and floor draw the stepped-to session — the header's title alone re-names itself to that record (its plan-name snapshot, `Freestyle Session` when it had none, back to the live name on today, 2026-10-23); the record's arrows walk records and the newest record's right arrow steps back onto today's live sets; a record that cannot be read — the stamp list outliving a row a sync round removed — drops the peek with a SnackBar and re-reads the stamps, so the arrow heals onto the next record instead of pressing into nothing (2026-10-23). Leaving the Training page drops the peek; the live session is untouched throughout. `SessionViewModel` is a **`ChangeNotifier` with mutable fields** (not an immutable state class); its rows come from PowerSync `watch` streams (subscribe on start/restore, cancel on end/reset).

**Planner** (`lib/features/programs/view/plan_session_screen.dart`) plans a future session inside a program or standalone. It shares the pushed `ProgramDetailViewModel` (`ProgramDetailState`, immutable `ValueNotifier` + `copyWith`), persists reorder to `dim_planned_session_exercise.exercise_order`, and uses `SessionSetRow` mode `planned` (free-text targets). It is a **session surface since 2026-10-26**: the same flat card on the same 22pt gutter, and the same two-row floor — `SessionDateBar.plan()` (a lone `PLAN`, both chevrons spent, no radios, the phrase inert), the undo/redo pair with the trash slot (spent — a planner deletes a group outright and undo is its way back), the star (spent — a plan has no session ratings), and `SessionStatsTiles(gain: false)` whose counts are the active exercise's whole PR feed, open goals and notes shelf and whose three doors open `showPrHistorySheet` / `showExerciseGoalsSheet` / `showLessonsModal` — the bullseye rides the planner too since 2026-10-27, lit by the exercise's open goals (the editor's own `goalTimeline` + `loadGoals`, written by `createGoalFromTarget`) — all scoped by the review checkpoint when the plan is edited inside a pass. The custom stats pill (SETS · EXERCISES) and the review-mode undo storey are gone with the custom floor. Deliberately absent: rest timer, feeling picker, ghost targets, the stack walk (a plan stands in no stack) — the fields themselves are the targets.

**Past-session viewer** (`lib/features/logs/view/session_detail_screen.dart`, route `/logs/:sessionId`) **is the Training view, read-only** (2026-10-22): no tabs, no caption bar — the **header names the session** (plan name, or "Freestyle Session") with `edit_outlined` / `check`, the same flat card draws the sets on the same 22pt gutter, and the same floor bar carries the date bar (`PREVIOUSLY - 20 Oct 2026`; live says `TODAY -`) with its chevrons walking **EXERCISE by default** (2026-10-23 — the active exercise's own earlier performances swap onto the card while the record stays the page; the bar's radios restore the whole-record walk) — **in place** (2026-10-22): `walkTo` steps the same VM onto the neighbouring record, the page never navigates (the left record stays on screen while the new read lands, never a spinner; edit mode, drafts and the undo stack are left behind, and Done writes the record on screen, not the route's id), and only the newest record's right arrow onto today is a real move — a pop onto the live page when the route was pushed from it (`fromLiveExtra`, the recap card), else `go('/session')` (the live page's own date bar never pushes: it peeks in place); no live session greys it (`SessionWalk` in the VM, guard-aware like the back arrow), then undo/redo with the historic trash in its slot (both modes; spent in view mode), the star, and the PR · goals · notes doors. `SessionDetailViewModel` (`ValueNotifier<SessionDetailState>`) drives it, view/edit modes. The star opens the ratings sheet read-only in view mode, editable drafts in edit mode, persisted by Done (`saveNotes` → `updateSessionNotes`; the sheet's own pencil, just left of its X, flips the same mode — accent glass while editing, absent on the peek, the preview and a friend's record, 2026-10-27); the trophy opens `showPrHistorySheet` — the PR Lab's PR History feed for the exercise on the card, with WEIGHT / REPS / VARIATION filters, read chronologically newest first (2026-10-23): `AFTER` on top, drawn only when non-empty, then the record's own shelf split by its set ids and headed `THIS SESSION` only on the live page or by the record's date (`20 OCT 2026`) when it is a past record, then `PREVIOUSLY` — and the note glyph the same exercise's exercise-notes modal, the same three shelves with its own drawn by `sessionId` and the same start on both sides. All three doors are scoped to whichever date the bar shows (this record, the peeked one, or today's live session), so a walk moves them — the bullseye lists the card's exercise goals, Open first behind its status filter and sortable by target date · weight · reps · newest, a met goal in success ink (2026-10-26), and its bar control lit while any goal is open (2026-10-27); the doors open at any count, so a `0` never hides the exercise's whole story (2026-10-23). Exercise order comes from `fact_session.exercise_order` (fallback: first appearance; edit-mode reorders persist back). PR detection is the derived engine; a plan-linked exercise draws no card rim (2026-10-23) — the blue lives on the selector field and the set rows, and freestyle is flat; per-row `parent_set_id` links render as history. Edit-mode keystrokes debounce (2026-10-13): one write per settle, patching the grid **and** the timeline's copy (`historyByExercise`), then re-deriving PRs — zero queries per keystroke. Deleted exercises are read historically (2026-10-14): a slot whose rows are all flagged keeps its number, the selector gives it the deleted box, its sets draw red and inert (emptied cells still ghost the plan's targets), the floor's trash lists them, and a **Restore button under the card** brings everything back (direct in edit mode, behind an "enters edit mode" confirm in view mode, so every restore is undoable). `?tab=` is accepted and ignored; `?exercise=` still selects.

Shared: `SessionExerciseCard`, `SessionSetRow` (`live` / `planned` / `history`), `ExerciseSelector`. The consistency rules are the `session-ux-consistency` skill.

**Goals from the floor** (2026-10-26, replacing the set row's swipe door; a numbered door on all three floors since 2026-10-27): a target is opened from the exercise, not from a set — the floor's control row is `star · trophy · bullseye · notes`, and the bullseye is one of `SessionStatsTiles`' three doors (a `success` `BarIconButton` until 2026-10-27) that the widget draws only when the surface hands it `onGoalTap` (the live Training floor, the past-session viewer **and** the planner / review workout editor do; a friend's or athlete's record passes none — the write would file under their id). No door draws a number (2026-10-27): the bullseye's open goals ride only its semantics, and the bullseye wears the accent glass while that count is above 0, like the trophy and the note once their own feeds are non-empty (the star stays neutral). It opens `showExerciseGoalsSheet` (`lib/features/goals/view/exercise_goals_sheet.dart`) on the PR History sheet's furniture (uppercased exercise eyebrow, title, count, close) over the exercise's goals: **Open** by default — the `SheetFilterField` status control adds Achieved / All — and ordered by the app's `SortButton` (target date · weight · reps · newest), each goal read met through `goalCompletionSet` over the same merged timeline the `G` badges come from (`SessionViewModel.goalTimeline` / `SessionDetailViewModel.goalTimeline`), a met goal in success ink with its completion day and an open one in content ink. Its New goal door opens `showAddGoalSheet` seeded with just the exercise (a one-shot `seed:`; the goals screen keeps its long-lived `draft:`), the write lands as a **standalone** goal (`ProgramRepository.createGoal`, program and block null — the planner's write is `WorkoutEditorViewModel.createGoalFromTarget` over the same repository), and the sheet live-rebuilds through a `Listenable` + getter with the G badges re-derived in place. The set row's drawer is Note / duplicate / delete again, and a PR that achieved a goal draws **green** in `showPrHistorySheet` (the same `goalSetIds`), not accent.

**The planned grammar** (2026-10-23, live rows only — the viewer and planner read, they never chip): a `planned` target in the empty cell is a **guide** in `planned` ink; a real value that meets the plan wears the **white-on-blue chip** (`plannedText` on `plannedFill`); a real value off the plan is plain `primary`. Weight chips on equality to a single number, reps on equality or inclusive range containment; a plan-linked row wears the `plannedBg` tint while no typed value contradicts a parseable target (non-numeric targets constrain nothing; notes never retire it), and `ExerciseSelector`'s closed field carries the plan (`planned: true`). The variation cell sits outside the guide grammar: a planned variation is a **real value** — categorical, not a target — drawn in `primary` and adopted into the row by its first commit (2026-10-23). Deleted outranks both everywhere.

## Timeline cache (`lib/data/cache/past_sets_timeline_cache.dart`)

The past-sets timeline is the app's most-read, most-expensive query, memoized per user (2026-10-13). The logs list, session detail, exercise detail and library usage all read `PastSetsTimelineCache.get(userId)`, which also keeps an oldest-first copy (`asc`) for `prEventsSorted` callers. Invalidated by every fact write in `SessionRepository` (the single funnel — its test walks every write method), the dev sample-data seeder, the Flow Lab's database swap (both directions), sign-out, and **once per remote-download sync round** (the `statusStream` `downloading` false→true flip in `openDatabase`).

**Recent-use ordering** (2026-10-26) derives from that one timeline. `PastSetRow.plannedSessionId` carries `fact_session.planned_session_id`, and `exercise_usage.dart` owns the two rules: `lastUsedByEntity` (exercise/variation) and `lastUsedByPlannedSession` + `compareByLastLogged`/`sortByLastLogged` (workout templates — most recently logged first, never-logged below every logged one, then newest created, then id). The library workouts listing, the Training template selector (re-sorted in the VM from the live timeline so a just-ended session floats its template) and the review picker all speak that order; a **program** listing keeps `sequence_order` — that is the plan's shape, not a usage list. Exercise and variation pickers already order by `lastUsedByEntity`.

## How planned sessions work

A template is three tables: `dim_planned_session` + `_exercise` + `_set`. Targets are **background values** — free text by design ("8-15", "AMRAP", "3 RIR"). There is **no validation** tying what gets logged to what was planned. Program membership is M2M via join rows; schedule slots (`sequence_order`, `day_of_week`, `week_offset`) live on the join row; progression mode ('frequency' | 'order') lives on the **run**, chosen at start.

**Start** (`SessionViewModel.startWorkout`) → `createSession` writes `fact_session` with `planned_session_id` and `end_datetime` NULL, then materializes the plan two levels deep: one `fact_session_exercise` per planned exercise (`planned_exercise_id`, `exercise_order`), then one `fact_session_exercise_set` per planned target with `planned_set_id`, `set_number` copied and reps empty. A planned **single-number weight** is recorded as the row's real weight at Start ("record weight at start if it is a real value", 2026-10-23); **reps are always guides**, even "5" — and a weight range never becomes a value. Ghost hints look up by `planned_set_id` — id-anchored, never positional; actual weight/reps are strictly numeric. `lib/core/utils/planned_target.dart` is the one parser every reader uses.

**Log** — typing commits to the row's own id. **End** (`endSession`) flushes pending edits, prunes untouched planned rows, sets `end_datetime = now`. A plan-linked row is untouched when it has **no reps, no variation and no notes** — a weight alone is an adopted hint, not a performance (2026-10-23); user-added rows and flagged rows always persist, empty ones included. **Restart** restores the template from the persisted `planned_session_id` and re-pairs rows by planned ids.

**Repeat** ("From past session", 2026-10-26) — the idle Training page's template picker carries a `From past session` door under its lists, opening the same browse sheet with completed records (`_SessionPickerSheet(seedMode: true)`); picking one calls `selectPastSession` (`SessionViewModel`), which reads the record's `exercise_order`, resolves its template live, and stores a `PastSessionSeed` (`lib/features/session/model/past_session_seed.dart`). `startWorkout` then branches on the seed: it writes `fact_session` with the record's own `planned_session_id` and the template's live name (the record's snapshot as fallback, both null for freestyle), **`program_run_id` = null** (a repeat is not the run's next session and must never advance its cursor), and `_materializeSeededSets` writes the record's arrangement — same tab order, one row per performed set with the numeric kg **real**, **reps empty** (a rep count is today's performance; the plan's guide or nothing draws in the cell), notes never copied, the record's variation copied **unless the plan target names one** (the card adopts the plan's), and `planned_set_id`/`planned_exercise_id` kept so the original plan rides underneath with **no new `dim_planned_session` rows**. The page's preview and this write both ask `PastSessionSeed.exercisesToCopy`, so what the user sees before Start is what lands. Picking a template or clearing the selection drops the seed, and `refreshProgram` leaves a seeded page alone (a tab switch must not re-choose the template underneath it).

Editing a template never affects logged sessions' VALUES (plain ref, no FK). **Names** are different: exercise and variation names live in the dims and update everywhere — renames apply to all past data, and the rename flows warn about it. The one name snapshot is `fact_session.planned_session_name`, written at session creation so a log keeps naming the plan it followed even after a template rename (exercise/variation snapshots were dropped 2026-08-26).

```
Program → PlannedSession → PlannedSessionSet
             │ startWorkout materializes fact_session + planned-linked rows
Active Session → SessionSet (parent_set_id → template row)
             │ endSession prunes untouched planned rows
Completed Session → Training Logs (review/edit)
```

## Programs, runs & reviews

A program either uses blocks (ordered, duration-bounded phases, length = weeks × 7 + days) or is a simple list; `uses_blocks` is stored at creation, never inferred. A **run** is the commitment to the program: starting one ends the previous current one, and **"End program" ends the RUN, never the program**. Order-based runs **wrap** (cursor = `completed % sessionCount`). Day scheduling and review scheduling are retired from the UI (data layer kept).

A **review is standalone** (`fact_program_review`; 2026-10-07): workouts and goals are picked directly, and `program_id` NULL means exactly that. `session_ids_json` is the ordered planned-session set, `goal_ids_json` the ordered goals, `reviewed_sessions_json` one timestamp per Done, `exercise_notes_json` keyed by `planned_exercise_id`, `workout_notes_json` by `planned_session_id`. `completed_date` NULL = open (no status column). `ProgramReview.sessionsIn` resolves any row (standalone stops at its stored set; otherwise stored set → single session → block's sessions → whole program) and `reviewScopeKey` is the canonical key, so a standalone pass over {A,B} deliberately chains with a program pass over {A,B}.

The **Library → Reviews tab is the only start surface** (`lib/features/reviews/`): `+` → name → the pass opens **empty** on its own landing, whose add tiles open the scope sheet (2026-10-27; the create-review picker screen is gone, and the scope can be built in any order — goals first is legal). The workout list is ordered last-logged then newest-created (`fetchReviewableRows`; `dim_planned_session` has no updated date). `beginReview` writes the row plus an "as found" baseline, idempotent so a resume never moves it; a workout or goal added mid-pass is merged into that baseline as it lands (`setReviewScope` freezes each addition at the moment the pass first covers it and never rewrites an entry it already holds, so Compare has a "before" for it), and the "at least one workout" rail now lives at the **finish** — `completeReview` refuses an empty standalone pass and the landing says so in a snackbar. An open pass's landing **always** carries Workouts | Goals (a record keeps the old rule: Goals only when it holds any); a workout opens the real editor with the bar's **Note · Compare · Done**, where Done is a toggle (`markWorkoutReviewed` / `unmarkWorkoutReviewed`, no settle on retract). That editor reads its template **with its removals in it** (2026-10-26): a group removed **during** the pass stays on the card — red name, red inert rows, its note box open to say why — while a group already gone when the editor opened stays hidden exactly as the planner draws it (the review's read brings back every archived group, so the editor pins the ids that predate it and never resurfaces them as this pass's removal), and Discard puts back only the removals the pass itself made (a group already gone when the editor opened stays gone). **A pass stages its edits, and the plan moves only at Finish (2026-10-27).** Inside a pass the workout editor is handed a `StagedPlannedSessions` (`lib/data/repositories/staged_planned_sessions.dart`) instead of the real repository — both implement `PlannedSessionStore` (`planned_session_store.dart`, exactly the editor's whole spend), so the editor never knows which it has. The staged store copies a workout **whole** into the pass's `ReviewStage` document (`lib/data/models/review_stage.dart` — the `PlannedSession.toMap` row plus every group and set map, archived rows included) on its first write, then answers every read and takes every write from there; the document rides `fact_program_review.proposed_content` (hash in `proposed_hash`) and is persisted after each write by `saveProposal` (open rows only; an empty stage clears the columns), so leaving the app mid-pass resumes into the same stage — the landing's cards read from it, Compare builds its "after" side through it, and Cancel is a **true discard**: `deleteReview` deletes the row and every staged edit with it, while the plan never moved. A workout the pass never touched stays out of the stage and keeps reading live. Goals are **not** staged — a target created or edited during a pass (the landing's goal sheet, the editor's goal door) writes immediately. The finish's snapshot drops the removed group, so the record shows the removal on BEFORE. **Finish** is landing-only, asks "N of M reviewed — finish anyway?" when work is unticked, then `completeReview` applies the stage row for row (the session's name/notes/date_archived UPDATE, then `INSERT OR REPLACE` of every staged group and set keyed on its logical id — nothing is deleted outright), writes the `ProgramContent` snapshot **built from the stage** (so it is of what the pass left) and stamps completion + outcome, clearing the stage — all in one transaction; a `dismissed` completion drops the stage without applying and writes no snapshot. The snapshot is the whole program for a program review, the set + picked goals for a standalone one. **Compare** diffs the newest COMPLETED predecessor whose set contains that workout, both sides narrowed to it, else the baseline. An open pass can be **cancelled** (swipe → confirm → `deleteReview`, guarded `completed_date IS NULL`); a completed record can be **deleted** (its own confirm → `deleteCompletedReview`, guarded `completed_date IS NOT NULL`). A completed review opens as a **record** (`ReviewRoute(readOnly: true)`, route name `kReviewRouteNameRecord`): the same landing read-only, and its workout cards open `RecordWorkoutScreen` over every **frozen version** of the workout (2026-10-26) — the current plan, then each completed review's end (`snapshot_content`, what the pass left) and start (`baseline_content`, what it found), newest first, all read at once by `fetchWorkoutVersions` so a step repaints and never loads. The record **wears the pass editor's whole floor** (2026-10-27): the same `KeyboardFloorLayout` under the review bar, with a `record-workout-bar` two-row floor — the version walker dressed in the session date bar's ghost box, naming `START OF REVIEW - 1 Oct 2026` / `END OF REVIEW - 9 Oct 2026` / a lone `CURRENT PLAN` and stepping older-left, newer-right, both ends spent — then the planner's actions row (undo/redo and the trash spent, the star disabled) beside live `SessionStatsTiles(gain: false)` doors, whose counts are the active exercise's whole PR feed, open goals and notes shelf and whose sheets are read-only (no New goal, `readOnly` exercise notes, the PR sheet checked against the pass's `sinceDate`); the exercise card is **flat**, like every session surface. `RecordWorkoutViewModel.loadContext` reads those shelves once after the page opens (the timeline through `PastSetsTimelineCache`, `fetchGoalOptions`, the lessons batch; each failure leaves its door quiet), so the record paints at once and its doors fill in behind it. The bar's label reads `Current Plan` over the plan and the side's name over a review's version. The eye became a jump between the two sides of the review on screen — offered only where both hold the workout — and the pair's marks both live on the **end** (2026-10-27): a green plus on what the pass added, and a red **minus** on each group its start held and its end does not, drawn from the start's frozen copy because the finish's snapshot drops the removed group — the card and its rows are the plain ones it had, so the mark alone says gone (2026-10-27, unlike the open pass, which still paints a group removed during it red); the start, being what the pass found, wears no marks at all. The current plan reads against the newest end, so its marks say what has changed since the last record. The review's notes ride only the versions it produced (an end), never its start. The proposal path is deleted; `proposed_content`/`proposed_hash`, born for it, now carry the pass's stage (2026-10-27). **Programs are out of the UI (2026-10-26)**: no Programs tab, no program routes, blocks, runs, history or copy-in, and every workout list (the session template picker and `fetchReviewableRows` included) reads **standalone** workouts only — a program-attached copy beside its library original read as a duplicate. The tables, repositories, screens and sync stay in place, unreachable, so programs can return without a migration; `fetchDueItems` never returns a standalone row, and nothing ever ends a run by itself.

## Friends (2026-10-23; note tiers 2026-10-26)

The social layer reuses the viewer rather than growing a second one. The nav is Session · Library · **Friends** · Profile · Dev, and `lib/features/friends/` holds the tab: the user's own shareable code (`dim_friend_code`, 8 characters from the look-alike-free alphabet, drawn `ABCD-EFGH`, copyable), an add-by-code sheet, and the friend list. Entering a code is the whole ceremony — friendship is **instant and mutual**, never a request; `add_friend_by_code` writes **two directed rows** in `friend_relationship` (one per side) and every read requires the pair: the `friends_data` stream's `my_friends` CTE and `are_friends()` in RLS both test both directions, so a half-pair grants nothing (and the RPC heals one it finds). The client mirrors **only its own directed row** (synthetic id `<userId>-<friendId>`); the reciprocal row is the RPC's alone — mirroring it would be an RLS rejection quarantined in `upload_failures`. The stream sends a friend's **completed** sessions only (the active one is never sent), their child rows, exercises/variations, lessons, goals and their rungs (`fact_goal_target`, 2026-10-26 — a goal row without its rungs would read as a goal with no target), a **name-only** `dim_user` slice, and each friend's **code** (2026-10-25 — the list's last-resort name; body metrics and profile stay private). A friend reads **nickname → their own name → their code → `Friend`**: the nickname is the caller's private label on their own directed row (never sent to the friend), and rename is swipe → pencil → nickname sheet. **Note tiers (2026-10-26, #23):** a friendship shares training by default — completed sessions, their sets and set notes — while **exercise notes and a session's pre/post notes** are a second tier the owner opens **per friend** (`friend_relationship.share_notes`, default false, the row's third swipe → privacy sheet; tier 1 is drawn as always-on). The friend never sees the flag; the gate lives in the `friends_data` stream (`dim_lesson` only for sharers, `fact_session` split into two disjoint queries with `NULL AS pre_notes/post_notes` for the rest, since RLS is row-level and cannot mask a column), with `friend_shares_notes()` as the REST half on `dim_lesson` — `sync-contract` owns the queries. Tier 3 — someone planning on your behalf — landed as **coach-only authoring** in #24: a friend still cannot hand you a workout (see Coaching). Tapping a friend opens `LogsScreen(userId:, readOnly:)` and the past-session viewer pointed at their id — `SessionDetailScreen(userId:, readOnly:, navRoute: '/friends')`, the same Training view with the edit star and every other write affordance gone, and `showLessonsModal(readOnly:)` drawing the shelves without the composer, pin or drawer. PRs and goal badges derive from the friend's own cached timeline (`PastSetsTimelineCache.get(friendId)`); the global `PrService` cache is never used on this path. Removal is swipe → confirm → `removeFriend` (RPC + the local own-row delete + `PastSetsTimelineCache.invalidate(friendId)`). The friend's session viewer is a top-level route (`/friends/:userId/sessions/:sessionId`) drawing its own bar, which lights the Friends tab through `navRoute`. Tables and RLS: `app-features`; upload maps and the stream: `sync-contract`.

## Coaching (2026-10-26)

The coach's read path reuses the same viewer a third time, and the edge is a **request/accept pair**. `coaching_relationship` (coach + athlete, composite PK) has `accepted_date` as its **consent gate**: a row without it is an invitation, and the `coaching_data` stream's `my_athletes` CTE requires it, so **nothing about that athlete — not even a name — reaches the coach's device** (`sync-contract` owns the query). The gate is asymmetric: the coach's own name reaches the athlete from the invitation on (a second `my_coaches` name slice), because nobody can consent to an anonymous request. Three SECURITY DEFINER RPCs are the only writes — `coach_invite_by_code` (resolves the athlete's friend code and writes the pending row), `accept_coaching_invitation`, and `remove_coaching_relationship` (decline / withdraw / revoke / withdrawal of consent, from either side) — and the client mirrors each locally. The two client write policies are shaped for those mirrors alone: a coach may insert only an unaccepted row, the athlete may update only their own. Every per-table coach SELECT policy now carries `accepted_date is not null`, so REST refuses what the stream refuses. The coach's own relationship rows ride `user_data`, so the local mirror sees pending edges.

The one Coach surface serves both sides: Profile → **Coach** (`/profile/coach`, `lib/features/coach/`) draws incoming invitations (Accept / Decline), the athletes the caller coaches, the caller's own coaches, and nameless pending-sent rows with a swipe to withdraw. An accepted athlete opens `LogsScreen(userId:, readOnly:)` → `/profile/coach/:athleteId`, whose cards open the top-level `/coach/:athleteId/sessions/:sessionId` viewer — `SessionDetailScreen(userId:, readOnly:, navRoute: '/profile')`, the friend path's exact read-only rules (no edit, no Restore, no lessons composer) and the athlete's own `PastSetsTimelineCache` for PRs and goal badges. The athlete route is nested under `/profile` so the pushed list keeps the Profile tab lit; only the session viewer is top-level, because it draws its own bar. The stale `ps_crud` purge for `coaching_relationship` is gone — the table now syncs, so a queued coaching write is a real upload.

**Authoring (2026-10-26, #24).** A coach hands an athlete a workout and writes notes on their sessions. `fact_coach_assignment` is an **offer, not a shared row**: it carries a frozen `ProgramContent` snapshot plus `names_json` (only the ids that workout uses), because `dim_exercise`/`dim_variation` rows are per-user — the coach's ids mean nothing in the athlete's library. The athlete's **Accept** decodes the snapshot, resolves each name against their own dims (`findExerciseByName`, creating when missing and reactivating when archived; an unresolvable group is skipped), and writes a fresh `dim_planned_session` + groups + sets in **one local transaction**, stamping `dim_planned_session.coach_assignment_id` so the copy keeps its provenance (`PlannedSession.isCoachAssigned`; the athlete's copy is theirs to edit and never tracks the original). Decline stamps `declined_date`; withdraw is the coach's local DELETE while `accepted_date is null`. The Coach screen gains **ASSIGNMENTS TO YOU** for the athlete (name, sender, note, Accept / Decline) and **ASSIGNMENTS SENT** for the coach (Awaiting reply / Accepted, swipe to withdraw while pending), and each athlete row swipes to **assign** — a sheet picking one of the coach's own workouts plus an optional note. **Feedback** is `fact_coach_feedback`, **one row per (coach, session)** (unique index): the coach writes it on the athlete's session viewer (`SessionDetailScreen(canCoach: true)` → the feedback card's Leave / Edit door, a multiline sheet with delete behind a two-verb confirm), the athlete reads the same card on their own record, and a friend's record never draws it — the stream sends feedback only to its two parties. Both tables ride `user_data` on an either-side predicate (`coach_user_id = auth.user_id() OR athlete_user_id = auth.user_id()`) — the `coaching_relationship` shape — because both sides read them; `coaching_data`'s athlete consent gate would hide an invitation from the athlete who must decide it. Tables, RLS and the CRUD matrix: `app-features`; the queries: `sync-contract`.

## PR methodology

PRs are **fully derived on read** — no table. Per (exercise × variation) pair (null variation is its own key; bodyweight is weight 0), a set `(w, r)` is a PR iff it extends the best-ever frontier — no prior set did ≥ r reps at ≥ w weight. One set = **one `PrEvent`**, even when it beats both dimensions at once; each event carries the two previous frontier values it beat (`beforeWeight` / `beforeReps`, both null = "First PR"). Counts, accents, badges and modals all count events — one number everywhere. Lenses (`repMaxCurve`, `weightMaxCurve`, `repAxisHistory`, `weightAxisHistory`) are insights-only projections that never gate detection. Editing past data self-heals on the next read. Engine: `pr_engine.dart` via `pr_service.dart` (memoized, `invalidate()` after any set write) and `_recomputePRs` in the live/logs VMs, fed by `PastSetsTimelineCache`'s oldest-first copy. Full spec: `docs/pr_methodology.md`.

## Key conventions

1. **Auto-commit + debounce** — real set rows commit on every keystroke; keystroke commits carry `immediate: false` and merge into **one write per 250ms settle** (`SessionViewModel.kAutoCommitDebounce`). Every flush point (blur, tab switch, wizard page change, app lifecycle pause/inactive/detached, session end) cancels the timer and writes immediately. Draft rows commit on blur only and are flushed at those same points; rows register commit handles with the VM.
2. **Numeric input** — live/history cells allow `^\d*\.?\d*$`; planned cells allow ranges (`[0-9.\-\s]`).
3. **Draft rows are freestyle only** — virtual rows that materialize on any user entry (weight, reps, variation or notes). Planned rows are real rows from materialization; there is no empty-row filling.
4. **Exercise order** — planner persists to `dim_planned_session_exercise.exercise_order`; the session persists to `fact_session_exercise.exercise_order` and restores on hot restart; the viewer orders by the same column. Reorder is a structural undo action.
5. **History** — `groupHistoryByExercise` (`session_local_state.dart`); read-only in planner/logs, editable in the live session behind a confirmation gate.
6. **Supersets retired** (2026-08-14, column dropped 2026-08-24) — no UI creates or emphasizes them; dormant slot support remains and a restored multi-exercise slot renders as its first exercise.
7. **Preview mirrors the session UI** — `_SessionPreview` is a read-only adapter over the shared card/row, never a hand-rolled layout.
8. **Soft-delete of planned rows** (2026-10-13, widened 2026-10-14) — deleting a set flags `fact_session_exercise_set.is_deleted = 1` instead of removing it, keeping `set_number` and the exercise row. The widened rule: a set deleted under a **plan-linked** exercise flags whatever its origin, so the exercise's Restore brings back everything underneath it; only a row of a user-added exercise hard-deletes (undo is its way back). Flagged rows stay visible red in their number place, and a **Restore button under the card** appears whenever the exercise on screen holds any (live: `restoreDeletedSetsForActiveExercise`; viewer: direct in edit mode, confirm in view mode). Flagged rows survive `endSession` (`_pruneUntouchedPlannedRows` only removes untouched ACTIVE planned rows) and `_persistExerciseOrder` writes the full arrangement with deleted slots spliced back, so a deleted exercise keeps its number. `loadSetsForSession`/`watchSetsForSession` return flagged rows; `loadPastSetsTimeline` and `loadSessionsWithSets` filter `COALESCE(s.is_deleted, 0) = 0` in SQL, which keeps PRs, goals, achievements, usage counts, history pickers and the logs list clean. Live opens a deleted exercise for reading through the stats bar's trash (`MenuPopover`, eye per row) → `deletedViewSeId`; the deleted view's selector **lists every deleted exercise** (the viewed one open; picking another flips the card in place, no write), the card draws no rim, empty rows keep ghosting their planned targets, and the Restore button does the write (un-flag, re-add the tab at its old slot, persist, undoable). Undo/redo are greyed while that view is up. In the viewer the trash works in both modes and lists by arrangement order (historic deletion order is not stored). Editing a past session soft-deletes exactly like the live one. Migration: `20261013120000_soft_delete_session_sets.sql`.
9. **Two devices, two live sessions** (2026-10-15) — every session is stamped with `fact_session.device_id` (uuid from `DeviceId`, `lib/core/utils/device_id.dart`). `getActiveSessionId(userId, deviceId:)` resumes only the caller's own (null device id falls back to any-active, because crash recovery outranks the distinction); `watchActiveSessions` feeds the another-device notice (Switch / Stay — Stay dismisses for the run; Switch adopts, asking first when this device has a session in progress). `claimSession` rewrites `device_id` so the next launch resumes there. A NULL device id reads as another device's — the safe reading. Migration: `20261015120000_session_device_id.sql`. **The notice floats, it does not sit in the page** (2026-10-27): the wizard publishes it through `sessionAboveBarNotice` (`session_screen.dart`) and the shell's `_TabShell` draws it in `ScrollShrinkNavBar.aboveBar`, so it wears the nav bar's `FloatingGlass` one storey up, and `FloatingBarOverlay` **measures** that storey's height (a notice is as tall as its words, not a bar's 56) into `contentInset` — every page below clears it with the bar. It shows only on the screens **before the live one** (`showsForeignSessionNotice`: Home and the pre-questionnaire), never over Training / Summary / post, and steps aside while a page covers the wizard (`didPushNext`/`didPopNext`) — the preview's own Switch band is then the floor. The preview is a stack of three storeys (viewer floor → Switch band → nav bar): its band, not the floor, spends the bar's clearance (`SessionDetailView.floorBottomInset`, 2026-10-27), and its push is the wizard's navigator, not the root's, so the bar keeps floating over it.
10. **Undo/redo** (2026-10-13) — `ActionUndoHistory` / `UndoAction` (closure-based, cap 50, redo cleared on push) in `lib/core/utils/undo_history.dart`. Each edit surface wraps its STRUCTURAL actions (add/remove/reorder/duplicate, drafts) with `_recordUndo`; typed value edits deliberately never enter the stack. `undo()`/`redo()` flush pending debounced writes first; insert ids live in `UndoBox`es. History clears on planner close, logs `startEditing`/dispose, and live reset/start. Buttons: `UndoRedoButtons` (planner header, logs edit header, live stats bar) — inside a review the planner's pair leaves the header for the floor storey above the review bar (2026-10-26; the bar's own row is full at 402pt, and the storey is where the live session keeps its pair).
11. **Text, names and keyboard** — text boxes follow `frontend-design` §6 (one tier above their ground, `elevated: true` on a card); every user-created name draws through `UserNameText` and is capped at 20 (`lib/core/utils/name_limit.dart`), enforced four deep: `maxLength` + `NameLimitCounter`, Save gated on `nameTooLong`, a VM error instead of a silent return, and a repository `_assertNameFits` that grandfathers an already-over-cap row (so a discard can never be blocked by a rule that arrived after it). The DB rail is 120 on all five wider columns because the mirror has no CHECK. Notes are uncapped prose. Keyboard dismissal is the frame's job: `KeyboardDismissOnTap` wraps the app root; never add per-field `onTapOutside`; scroll-to-dismiss is opt-in per screen.
12. **The Library** — its five tabs (Exercises, Variations, Workouts, Reviews, Goals) share one toolbar of `LambdaSearchField` + compact `GlassButton`s and one header `InfoButton` that explains the active tab. The **Reviews** tab filters through `DateRangeSelection`, and a date range narrows only completed passes — an open pass is never hidden. The **Goals** tab is sections and subsections (exercise → variation) with pinned headers, **collapsed by default** (the section a goal was just added to opens); sort defaults to By exercise; filters (status, target-date window, completed-date window) AND together; a goal card states **one** date (completion behind a green check, else deadline behind a bullseye) and wears the success chrome when met; the focused goal sheet rests read-only with Edit, and SAVE only enables when the draft differs. A goal is **single-set** (one weight × reps pair, the parent columns) or **multi-set** (a rung list in `fact_goal_target`, the composer's Single set / Multi-set switch): every rung means "this set or better" and all must be met by **distinct** sets — one strong set cannot tick two rungs, and greedy rung order is not the rule (the engine is a bipartite match), so the `G` marks every witness and the goal completes on the set that finishes the match. Every deletion in the library has its own confirm — goals and reviews behind a deliberate swipe, workouts delete-vs-archive, exercises and variations likewise.
13. **Glyph or word** — glyph when the control operates the frame (header nav, toolbar and row actions), word when it is the point of the screen (primary CTAs, dialog verbs, count-carrying pills, filter chips, one-off actions). Icon-only = `label: ''` + `icon` + `semanticsLabel` on a ≥40px target spent inside the content. The session wizard's seven verbs are the reference. A back-door warning offers **two verbs, never three** (2026-10-23): `UnsavedChangesGuard`'s dialog is Discard / Stay — Save is the screen's own button, never a third way out, because a warning that can write puts an accidental commit one tap from a back gesture; only the review settle, which has no discard side, reads Save and finish / Stay. See `frontend-design` §5.
14. **Preventing drift** — a new size, weight, ink, or spacing is chosen from a skill's table and added to its token file first. If a screen needs a value that does not exist, the token (name, not number) and its doc line land in the same change. This is what `typography` and `accessibility` exist for (2026-10-21).

The 2026-10-21 readability pass (12px floor, `inkSecondary`, prose line height) landed there, rolled out app-wide on 2026-10-22, and is guarded by `test/support/readable_text.dart` (`expectReadableText`) plus `test/typography_guard_test.dart` (no production numeric size below 12, no tracking beyond 0.8). **The Visual Pairings study** (`/dev/visual-pairings`, 2026-10-28) was the read/edit language lab: the same PRE-WORKOUT section under three candidate rules (Today · Frame · Hollow — one border in both modes, the fill moving with the mode), one READ | EDIT switch per card. **C · Hollow won and was swept into the shared widgets the same day** — `LambdaReadout` is the field hollowed and `FeelingRating`'s pill fills only while it takes a tap — so the page's "Today" card now draws C too; it stays as the decision's record, with A · Frame kept as the road not taken.
- **Release builds** — if a release build on device misbehaves while debug works, start from `docs/release_only_crashes.md`, not from app code; the `release-crash-triage` skill has the checklist. Watch for `+eol` packages (`grep eol pubspec.lock`) — a retired mechanism is what broke the 2026-09-30 release build (`powersync ^1.8.0 → ^2.4.0`).
- **Device installs** — installing via `devicectl` **wipes the device's local database**; flag that before doing it, since unsynced writes are lost. iOS/Xcode 27 constraints are in the `ios-toolchain-xcode27` memory.
