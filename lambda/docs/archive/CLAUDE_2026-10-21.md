Naming rules (2026-08-13 redesign, 2026-08-26 amendment): `dim_*` = reference data. Top-level dims (exercises, variations, planned sessions, programs) soft-delete via `date_archived` timestamptz (NULL = active — sortable, latest archived first); their child tables and `dim_lesson` keep the boolean `is_archived` (internal lifecycle only). `fact_*` = events. "Workout" language is banned in the DB — templates are **planned sessions**, logged workouts are **sessions**. See the `app-features` skill for the complete table inventory, RLS matrix, and sync wiring; the `sync-contract` skill for schema/sync changes.

## Core Architecture: The Three Session Screens

The app has three session surfaces that share one UX. **The live session screen is the primary design foundation** — the other two mirror its patterns via shared widgets (see the `session-ux-consistency` skill for the rules).

### 1. Session Screen (`lib/features/session/`) — Active Training

**Purpose:** Log a live workout in real-time. The most feature-rich screen.

**Structure:**
- `view/session_screen.dart` — `SlidePages` wizard, 5 pages (indices are `SessionViewModel.k*Page` constants): 0 = Home (congrats banner + last-session recap, Start), 1 = Pre-Questionnaire (feeling/notes + last-session recap, Continue), 2 = Training (active workout; idle state shows `_SessionTemplateCard` template picker + `_SessionPreview` read-only preview), 3 = Summary (THIS SESSION recap, Finish Session), 4 = Post-Questionnaire (feeling/notes + completed-session recap, Done → Home). Pre answers are written at session creation (Training's Start); post answers via `updatePostQuestionnaire` on Done, after `endSession` stamps only `end_datetime`.
- `viewmodel/session_viewmodel.dart` — `SessionViewModel`, a `ChangeNotifier` with mutable fields (NOT an immutable state class).
- `view/live_exercise_card.dart` — `LiveExerciseCard`, a thin adapter over the shared `SessionExerciseCard`/`SessionSetRow`.
- Renders: `SessionExerciseCard` (with `ExerciseSelector` pills, pinned lesson, Lessons/History/PRs pills) → `SessionSetRow` grid + rest timer + stats bar.

**Key features (priority order):**
- Exercise selector (pill popover: switch, arrows reorder, add — removal is un-ticking a row in the add-exercise modal)
- Exercise card: planned outline, PR count badge, pinned lesson bar, history picker
- Inline editable set grid: REPS/KG/VARIATION/NOTE columns, `SessionSetRow` (mode `live`):
  - `FilteringTextInputFormatter` numeric-only weight/reps
  - Auto-commit on blur (weight/reps)
  - Ghost planned-target hints (planned text from the linked dim row)
  - PR accent row (background + border turn accent)
  - Swipe-to-duplicate, swipe-to-delete
  - Variation dropdown with "Did you mean?" dedup + inline create-new
  - Notes icon modal
- Stats bar: SETS / PRS (tappable → PR modal) / EXERCISES / AVG REST
- Rest timer bar + hold-to-finish End Workout
- Home page: congrats banner (with the finished session's stats), last-session recap card, Start
- Pre-questionnaire page (after Start): feeling picker (1-5), pre-notes, last-session recap card — nothing persisted until the workout starts
- Post-questionnaire page (after Finish Session): feeling picker, post-notes, completed-session recap card — Done writes the answers and lands Home

### 2. Planner Screen (`lib/features/programs/view/plan_session_screen.dart`) — Planned Session Editor

**Purpose:** Plan a future session (template) inside a Program, or standalone.

**Structure:**
- Pushed via `MaterialPageRoute` from `program_detail_screen.dart`
- Shares the same `ProgramDetailViewModel` (constructor param)
- `ProgramDetailState` — immutable `ValueNotifier` with `copyWith`
- `_PlanExerciseCard` — adapter over the shared `SessionExerciseCard`; rows use `SessionSetRow` mode `planned` (free-text targets)

**Key features:**
- Editable inline header (tap to rename, auto-commit on blur), session notes
- Stats bar: SETS / EXERCISES (no PRs/rest — no live data)
- Exercise selector (arrows reorder → `exercise_sequence_order` persisted)
- Lessons/History/PRs pills greyed by decision
- Add exercise modal (single-exercise only — no superset)
- Save button (appears when dirty) + auto-commit on blur
- Delete session with confirmation dialog

**Deliberately excluded:** PRs, rest timer, feeling picker, ghost targets (the fields themselves ARE the targets).

### 3. Past-Session Viewer (`lib/features/logs/view/session_detail_screen.dart`) — Completed Session

**Purpose:** Review and edit a completed session from Training Logs.

**Structure:**
- Navigated via go_router from `logs_screen.dart` (`/logs/:sessionId`)
- `SessionDetailViewModel` — `ValueNotifier<SessionDetailState>` (immutable)
- Two modes: **view** (read-only) and **edit** (inline editing)
- Exercise tabs order from the persisted `fact_session.exercise_order` (fallback: first-appearance in set rows); edit-mode reorders persist back to it

**Key features:**
- Same shared card/row layout as live/planner (`_DetailCardBuilder` adapter; rows mode `history`)
- 4-tile stats bar: SETS / PRS / EXERCISES / AVG REST
- PR detection via the derived-on-read PR engine
- Planned outline (from `session.parentSessionId`); per-row planned linkage via `parent_set_id`
- Pre-workout feeling display (1-5 indicators)
- Edit mode: same set-row grid with swipe actions, add exercise, "+ ADD SET"
- Edit-mode keystrokes debounce like live rows (2026-10-13): the settle writes once, patches the row in the grid AND in the timeline's copy (`historyByExercise` — the history picker reads it), and re-derives PRs — zero queries per keystroke, one state update per settle; a failed write patches nothing. PR derivation is scoped to the slot exercises over the cache's oldest-first timeline via `prEventsSorted`.
- Pre/Post notes in footer bar (edit mode only)
- Lessons/History per exercise (same shared modals)
- **Deleted exercises read historically (2026-10-14)**: an exercise whose rows were all deleted during the workout keeps its slot at its number — the selector gives it the deleted box (red name container), its card wears the deleted outline (red), its sets draw red in place (`SessionSetRow.deleted`, inert in both modes), the trash button in the header (both modes) lists the deleted exercises and a row tap views one, and a **Restore button under the card** — shown whenever the card holds deleted sets, folded away or not — brings everything under the exercise back: in edit mode directly, in view mode behind an "enters edit mode" confirm, so the restore is always part of the edit session's undo history. Editing here flags sets under plan-linked exercises exactly like the live session (user-added rows of a user-added exercise still hard-delete).

**Excluded:** rest timer (no rest data), elapsed timer, superset display.

## Timeline Cache (`lib/data/cache/past_sets_timeline_cache.dart`)

The past-sets timeline is the app's most-read and most-expensive query, so it is memoized per user (2026-10-13). The logs list, session detail, exercise detail, and library usage reads all go through `PastSetsTimelineCache.get(userId)`, which also keeps an oldest-first copy (`asc`) for `prEventsSorted` callers. Invalidated by: every fact write in `SessionRepository` (the single funnel — the cache test walks every write method), the dev sample-data seeder, the Flow Lab's database swap (both directions), sign-out, and **once per remote-download sync round** (the `statusStream` `downloading` false→true flip in `openDatabase` — one invalidation per round, not per batch).

## How Planned Sessions Work

- **Template** = `dim_planned_session` + `dim_planned_session_exercise` + `dim_planned_session_exercise_set`. Targets are **background values**: free text by design ("8-15", "AMRAP", "3 RIR") — a plan is a hint layer, not a contract. There is **no validation** tying what gets logged to what was planned.
- **Program membership** = `dim_planned_session_program` join rows (M2M — one template can sit in several programs). Schedule slots (`sequence_order`, `day_of_week`, `week_offset`) live on the join row; progression mode ('frequency' | 'order') lives on the **run** (`fact_program_run.progression_mode`), chosen at run start.
- **Start** (`SessionViewModel.startWorkout`) → `createSession` writes `fact_session` with `planned_session_id` (FK) and `end_datetime` NULL, then **materializes** the plan two levels deep: one `fact_session_exercise` per planned exercise (with `planned_exercise_id` + `exercise_order`), then one `fact_session_exercise_set` row per planned target with `planned_set_id` = the dim row's id, `set_number` copied, actual values empty. Planned targets render as ghost hints looked up by `planned_set_id` (id-anchored, never positional); actual values (`weight`, `reps`) are strictly numeric.
- **Log** — typing commits to the row's own id. Weight/reps/variation/notes from the plan never prefill actual values.
- **End** (`endSession`) → flush pending edits, delete **untouched planned rows** (planned link + no weight/reps/variation/notes — they were hints, so logs show what actually happened), set `end_datetime = now`. **Empty sets are valid**: any row the user added or touched persists, completely empty ones included.
- **Restart** — restore loads the template via the persisted `planned_session_id` (not the default picker), and re-pairs rows by `planned_exercise_id`/`planned_set_id`.
- Editing the template never affects logged sessions' VALUES (the planned link is a plain ref, no FK). **Names** are different: exercise/variation names live in the dims and update everywhere — renames apply to all past data (the rename flows warn about this). No name snapshots exist (dropped 2026-08-26).

### Workflow: Plan → Log → Review

```
Program → PlannedSession → PlannedSessionSet
             │
             ▼ (startWorkout creates fact_session + materializes planned rows)
Active Session → SessionSet (logged; parent_set_id links to the template row)
             │
             ▼ (endSession: is_active = 0, untouched planned rows pruned)
Completed Session → Training Logs (review/edit)
```

## Programs, Runs & Reviews

- **Program shape** — a program either uses blocks (ordered, duration-bounded phases: `dim_program_block`, length = weeks × 7 + days) or is a simple list of workouts. `dim_program.uses_blocks` is stored, fixed at creation — never inferred. Workouts join via `dim_planned_session_program`; a run follows one block at a time (`fact_program_run.block_id`).
- **A run** (`fact_program_run`) is the commitment to doing the program. Starting a run ends the previous current one; **"End program" ends the RUN**, never the program. Order-based runs **wrap** — the cursor is `completed % sessionCount`, so carrying on past the length needs no new length. Day scheduling (day picker, Frequency progression) is retired from the UI (2026-10-03); data layer kept.
- **A review is standalone** (`fact_program_review`, 2026-10-07): **workouts and goals**, picked directly — `program_id` NULL means exactly that (`isStandalone`). `session_ids_json` is the ordered planned-session ids it covers, `goal_ids_json` the ordered goal ids at any scope, `reviewed_sessions_json` one timestamp per Done (so a pass's ticks persist across app exits), `exercise_notes_json` keyed by `planned_exercise_id` and `workout_notes_json` by `planned_session_id` (both written through as typed — not lessons, not carried forward). Legacy rows carry `block_id`/`session_id` instead — `ProgramReview.sessionsIn(links)` resolves any row to its set (a standalone row reads its own stored set and stops; otherwise stored set → single session → block's sessions → whole program, empty resolutions falling down the chain), and `reviewScopeKey` is the shared canonical key (sorted ids, legacy triple fallback), so a standalone pass over {A,B} and a program pass over {A,B} deliberately chain. `completed_date` NULL = **open** (no status column).
- **Starting one**: the **Reviews tab in the Library is the only start surface for now** (`lib/features/reviews/`) — `+` → name sheet → **selection screen** (tick workouts, tick goals; both lists offer everything the user has, whatever program it hangs off) → Start review. Goal-only passes are refused (≥1 workout). The workout list is ordered **last logged, then newest created** (`fetchReviewableRows`: `MAX(fact_session.created_datetime)` per `planned_session_id` desc nulls last, then `dim_planned_session.created_date` desc, then id desc) — `dim_planned_session` has **no updated_date**, so recency comes from logged sessions or not at all. **Beginning** (`beginReview`) writes the row plus an "as found" baseline from the live rows — idempotent, so a resume never moves it. Scheduling is retired from the UI (repo/VM plumbing kept, like day scheduling). An open pass can be **cancelled**: swipe its IN PROGRESS card (`SwipeActions`, danger) → confirm dialog → `deleteReview` hard-deletes the row, guarded `completed_date IS NULL` so a pass completed elsewhere survives. The ticks, notes, baseline and snapshot are columns on that one row — nothing else goes with it — and cancelling a scheduled pass also removes its `kDueReview` item (the only dismiss path one has). **A completed record can be deleted** (2026-10-19): swipe its COMPLETED card the same way → its own confirm ("Delete this review?", dismissed by "Keep it" — never the other question's verb) → `deleteCompletedReview`, guarded `completed_date IS NOT NULL` — the mirror of the cancel's guard, so a stale completed card can never take an open pass; the row is all that goes.
- **The pass**: the **landing** (`_ReviewLanding`) — **Workouts | Goals** tabs under the header, one card per workout (tick + date once Done) on the first and one per picked goal (tap → read-only view) on the second; a pass with no goals gets no strip, rather than an empty tab. Tapping a workout pushes the real editor (edit mode) with the review bar below: **Note** (workout-level, accent when one exists) **· Compare** (that workout) **· Done** (a toggle: the mark settles the editor → `markWorkoutReviewed`; the same tick again calls `unmarkWorkoutReviewed`, no settle — retracting a claim asks nothing). The workout stays open either way and the bar answers on itself: it reads the tick off `ReviewSession.reviewed`, so `setActiveWorkoutDone` moving the notifier IS the answer ("Review Complete" + green rim, or back to the pass's words; 2026-10-09). **Finish** is on the landing only; with unticked work left it asks "N of M reviewed — finish anyway?" before the notes sheet, then `completeReview` writes a `ProgramContent` snapshot and stamps completion + outcome in one transaction. The snapshot is **the whole program** for a program review and **the set + picked goals** for a standalone one (`buildContentForSessions`); reads narrow it (`contentInScope`, which keeps an explicitly picked goal even when its block holds no reviewed workout). **Compare** diffs the newest COMPLETED predecessor whose set **contains** that workout, both sides narrowed to it, else the baseline — a standalone review walks every review the user has, a program review its own. While the eye is up the plan's own tabs mark the names the record does not hold with a green **plus** (`ExerciseMark`, a filled disc so the stroke does not read as a hyphen against the name); a dropped exercise is never listed, so a live pass shows **no minus** — and the marks go with the flip, so a pass at rest is bare (2026-10-12). A dismissed review completes with no snapshot. The proposal path is deleted (2026-10-06) — `proposed_content`/`proposed_hash` columns stay, dormant. **A completed review opens as a record** (`2026-10-11`): tapping a COMPLETED card pushes `openCompletedReview` → `ReviewRoute(readOnly: true)` under its own route name (`kReviewRouteNameRecord` — a record must never be what `unwindReview` pops down to) — the same landing, read only: cards with no swipe and no add tiles, the ticks as recorded, the bar reading "Review Complete" over a green rim, and a third **Summary** tab ("Nothing here yet." — a placeholder for now, on records only). Nothing is published to `reviewSessionNotifier` and nothing writes — a record is not a pass, and the opener refuses while one is live. **A record reads** (`2026-10-12`): both lists are doors into readings. A workout card opens `RecordWorkoutScreen` — the pass's own chrome (header, shared card, the review's bar at the floor) over the record's **two frozen sides**: the baseline as `beginReview` found it and the snapshot `completeReview` wrote, both narrowed by `contentInScope`, never the live plan (which keeps being edited and would rewrite history under the reader). **The names carry the sides' disagreement** (`2026-10-12`): an exercise the side on screen holds and the other does not wears a green **plus** (added since the base) or a red **minus** (dropped) — `ExerciseMark`, each a plus or minus inside a filled disc, drawn on the shared selector's name in the field and in every popover row, one membership test with two readings so the marks can never disagree across the eye, names both sides hold bare, and no marks at all when the record kept only one side. The **eye flips between them** — `BEFORE · 8 Oct 2026` / `AFTER · 9 Oct 2026` on a page caption AND on the bar's own label, which on a record's workout names the side on screen (`kReviewAfterLabel` / `kReviewBeforeLabel`) rather than the walk: both of a record's documents are frozen, so the bar says which one is being read — green rim and words at rest, turning accent as the eye turns, through the label's usual rise — where a pass reads what the PASS is ("Review Complete" outranking what is on screen, "In Review", "Previously"); a record with only one side offers no eye. The bar is handed the row's `ReviewSession` (`reviewChrome(session:, readOnly: true, loadComparison:)`) rather than publishing one, the tick drawn wearing the record's answer and disabled — green under `GlassButton`'s half opacity when the record says Done — the note glyph greyed, and Compare/Changes reading those same two documents through the injected comparison. Every callback is null or inert (no reorder, no add, no ADD SET, Lessons/PRs greyed, the review's notes reading back — the exercise's box under its sets holding its place either way, `'No note'` where the review left none, the workout's above the card when it has one) with exercises switchable, because looking is not writing. The row is read on the route before the push, so the screen is plain data with no loading state; a row with no snapshot (a dismissed completion, a pre-snapshot row) says so instead of drawing an empty grid. A goal row opens the same `showGoalSheet` with no `onSave` — the sheet's **record** state (2026-10-19): the shared `ExerciseTargetPicker` form resting, no Edit, no way into the fields, no "Add a note…", and no NOTES section when the record left none; the completion row under the deadline still reads live history, which a review never froze. The program history panel keeps `showReviewDetailSheet` (the WHAT CHANGED diff the landing never shows).
- **Program/run surfaces are retired from the UI, plumbing kept** (2026-10-07): the program panel's Review button is gone (its history tab resumes passes, never creates them), and a length-reached run answers the prompt directly with **Continue / Change length / End run** (`_answerRunFinished`) instead of opening a review. `fetchDueItems` never returns a standalone row (`program_id IS NOT NULL`), and `kDueRunFinished` still needs `hasCompletedReviewForRun` — which is why **Continue no longer clears the banner**: nothing writes the completed review that satisfied it. Nothing ever ends a run by itself.

## ViewModel Patterns

1. **`ChangeNotifier`** (mutable state, `notifyListeners()`): `SessionViewModel` — the only one; mutable fields with derived getters.
2. **`ValueNotifier<State>`** (immutable state, `copyWith()`):
   - `ProgramDetailViewModel` with `ProgramDetailState`
   - `SessionDetailViewModel` with `SessionDetailState`
   - `LogsViewModel` with `LogsState`

Rule of thumb: complex state needing selective rebuilds → immutable state; tightly coupled logic with many derived properties → ChangeNotifier (session screen).

## PR Methodology

PRs are **fully derived on read** — there is no PR table. On every relevant read, the engine (`lib/features/session/model/pr_engine.dart`, used via `pr_service.dart` / `_recomputePRs`) walks logged `fact_session_exercise_set` history chronologically (2026-08-29 frontier redesign):

- **The definition**: a set (w, r) is a PR iff it extends its pair's best-ever frontier — no prior set did ≥ r reps at ≥ w weight (Pareto dominance). 100 × 5 after 110 × 1 IS a PR; 100 × 4 after 100 × 5 is not; an identical repeat is not. One set = **one `PrEvent`**, even when it beats prior records on both dimensions at once.
- **Scope**: per (exercise × variation) — null variation is its own key. Bodyweight is weight 0.
- **Before-facts**: each event carries the two previous frontier values it beat — `beforeWeight` (previous best weight at ≥ this many reps) and `beforeReps` (previous best reps at exactly this weight). A 100 × 10 after 6 × 10 and 100 × 3 renders "was 6 × 10 · 100 × 3". Both null = "First PR".
- **Counts, accents, badges, and modals** all use events (one number everywhere — the live stats bar and the logs summary can never disagree).
- **Lenses (insights only)**: rep-max curves, weight-max curves, and per-axis progressions (`repMaxCurve` / `weightMaxCurve` / `repAxisHistory` / `weightAxisHistory`) are pure projections over raw history — they never gate detection. `kTrackedRepCounts` is a display config for the insights curves, nothing more.
- **Edit-past-data self-heals**: correcting a set changes every PR view on the next read; no stale rows to clean up.
- **A PR can also be a goal's**: the same set may extend the frontier AND be the earliest set meeting a goal (`SessionSetRow.isGoal`). It is drawn once — as the goal (green `G`) — but the PR still counts: the stats tile, the exercise's PR count and the PR modal all include it. Visually a goal set, schematically both (2026-10-20).

Full spec: `docs/pr_methodology.md`.

## Key Conventions

1. **Auto-commit while typing** — real set rows commit on every keystroke (onChanged), so navigating away can never lose a value; blur commit remains as a safety net. Since 2026-10-13 keystroke commits are **debounce-eligible**: `SessionSetRow.onCommit` carries an `immediate` flag (keystrokes false, blur and the registered flush handle true), and the live/logs VMs merge the debounced ones into **one write per 250ms settle** (`SessionViewModel.kAutoCommitDebounce`) — every flush point (blur, exercise-tab switch, wizard page change, app lifecycle pause/inactive/detached, session end) cancels the timer and writes immediately, so only a hard kill within 250ms of the last keystroke loses that tail. The live session's rows then come from PowerSync `watch` streams (subscribe on start/restore, cancel on end/reset), so a settled write re-emits the authoritative rows — no manual patch, no reload. Draft rows commit on blur only (a keystroke must not materialize a draft mid-typing), and are flushed on app lifecycle pause/inactive/detached, exercise-tab switch, wizard page change, and session end (rows register commit handles with the VM).
2. **Numeric-only input** — live/history weight+reps cells use `FilteringTextInputFormatter.allow(RegExp(r'^\d*\.?\d*$'))`; planned cells allow ranges (`[0-9.\-\s]`).
3. **Draft rows (freestyle only)** — virtual rows that insert a fresh set on commit; a draft materializes on any user-entered value (weight, reps, variation, or notes). Planned rows are real rows from materialization — there is NO empty-row filling (that heuristic landed data on the wrong row).
4. **Swipe-to-reveal** — SwipeActions for Duplicate/Delete; delete is immediate.
5. **Lessons modal is polymorphic** — takes a `Listenable` + callbacks, works with both VM patterns.
6. **Exercise order** — planner reorder persists to `dim_planned_session_exercise.exercise_order`; session reorder persists to `fact_session_exercise.exercise_order` (a real column — the old JSON blob is gone) and restores on hot restart; the logs viewer orders by the same column.
7. **History** — `groupHistoryByExercise` from `session_local_state.dart`; read-only in planner/logs, editable with a confirmation gate only in the live session.
8. **initState defer** — VM methods that mutate `ValueNotifier` state synchronously must run post-frame via `WidgetsBinding.instance.addPostFrameCallback`.
9. **Supersets retired (2026-08-14, column dropped 2026-08-24)** — no UI creates or emphasizes supersets, and `superset_group_number` no longer exists (schema v2). Dormant slot support in the live session VM remains; a restored multi-exercise slot renders as its first exercise.
10. **Preview mirrors the session UI** — `_SessionPreview` is a read-only adapter over the shared card/row, not a hand-rolled layout.
11. **One text box, two halves** — editable text boxes are `LambdaInput` (the Pre-Evaluation notes field is the reference; dense search boxes are `LambdaSearchField`), read-only text boxes are `LambdaReadout` (the past-session viewer's display is the reference). A box's fill is one tier above its ground — `surface` on the page, `surfaceHigh` on a card or default sheet (`elevated: true`; 2026-10-08). Exceptions: inline header titles that ARE the header (chrome-less tap-to-rename), numeric cells (set grid — mono, centred), and the exercise card's review note box, which copies the Pre-Evaluation field by name — base fill, no step up (2026-10-08). Rule: `frontend-design` §6.

A filter or search that leaves nothing says so ("No goals match") instead of drawing an empty list; a failed add keeps the sheet and its typed target up (`GoalsViewModel.addGoal` returns `Future<bool>`). **Deleting always asks (2026-10-19)**: a goal row swipes to a danger drawer like Reviews' cards, and the drawer alone calls `confirmDeleteGoal` (`goal_dialogs.dart`) before the write — the card carries no × (2026-10-19), because a delete behind a deliberate swipe can be taken back before the question is even asked. That closes the library's set — every deletion in it now has its own confirm: goals, workouts (delete vs archive), programs (archive, and the archived bin's permanent delete), exercises and variations, and reviews' cancel/delete pair.
16. **Glyph or word (2026-10-20)** — a control is a glyph when it operates the frame, a word when it is the point of the screen. Header nav (back, close, edit, save/done), toolbar actions and row actions are glyphs (`HeaderIconButton` bare on a header, `GlassButton` icon-only in a toolbar); primary CTAs, dialog verbs, count-carrying pills, filter chips stating their value, and one-off actions (`Retry`, `Restore`, `Go to program`) keep their words. Icon-only means `label: ''` + `icon` + `semanticsLabel`, which is both the tooltip and the screen-reader reading; the lone glyph stands on a ≥40px target spent inside the content, never by stretching the container (a `Container(alignment:)` fills loose constraints and drags a `MenuPopover` panel off-screen — the 2026-10-20 bug). The session wizard's seven verbs are the reference: Back/Continue/Summary/Start/Cancel/End/Done.
17. **Names: capped at the field, never allowed to bleed (2026-10-20)** — `lib/core/utils/name_limit.dart` is the one spelling of the limits (**every kind is 20** — exercise/variation, workout, program, block, goal text, review title — because the narrowest surface a name is drawn on is the `PageHeader` title: 217–226pt of a phone header, ~20 average characters at `AppTextStyles.lg` w600) and every write path enforces them four deep: `maxLength` + `NameLimitCounter` at the field, a Save gated on `nameTooLong` (an over-long name must never offer a Save that no-ops), a viewmodel error (`nameTooLongMessage`) instead of a silent `return`, and a repository `_assertNameFits` (`ArgumentError.value`, the `ExerciseRepository` pattern) — which **grandfathers a row already over the cap** (`updatePlannedSession` reads the stored name first), because the workout discard path writes back the name the row was opened with and a rule that arrived after the row must not block its rollback. The display rule is a widget: every user-created name draws through `UserNameText` (one line, ellipsis, tooltip where the name is being chosen, `Expanded`/`Flexible` in a `Row`). The database rail is 120 on all five wider columns (`20261020120000_name_length_rails.sql`) — deliberately above every cap because the PowerSync mirror has no CHECK, so a trippable rule would quarantine the write instead of refusing it. Notes and descriptions are prose: uncapped and wrapping.

18. **Keyboard dismissal is the frame's job (2026-10-20)** — `KeyboardDismissOnTap` (`lib/shared/widgets/keyboard_dismiss.dart`) wraps the builder's output in `lib/app.dart`, so a tap on empty space unfocuses wherever a field is up — every shared text box, the set grid's raw cells and the two inline header renames included, with no per-field wiring. A tap that operates a control is not empty space: the control wins the gesture arena and its action runs with the keyboard untouched — and a tap on another field transfers focus directly, so adjacent set cells never blink. Do not add per-field `onTapOutside` callbacks: they fire on pointer DOWN (a field takes focus on pointer UP), which is the blink itself. Scroll-to-dismiss stays opt-in per screen — `KeyboardDismissOnScroll`, same file, today only the profile page (the session page must not dismiss while the user scrolls to a later set).

## Toolchain & Diagnostics

- **Startup (2026-10-13)**: `main` runs `Supabase.initialize` and `initializeDateFormatting` in parallel (the date formatting no longer waits behind the auth network round trip). The version gate is **cached-first**: the last check result is persisted (`VersionCheckStore`), a cached `updateRequired` blocks immediately while the live check re-verifies in the background (a live result that clears it swaps to the app — a post-update false-block self-heals in one round), anything else renders the app optimistically with a 3s fail-open live check. `VersionGateApp` takes `checkService`/`store`/`appBuilder` test seams.

- **Library read economy (2026-10-13)**: `ExerciseViewModel.fetchAll` is three reads (exercises + variations in parallel, then usage with the catalog passed in — the detail map derives from the list), guarded load-once; mutations patch state in place (rename/delete/create insert locally — a create carries the active spelling, no archived date), `refreshExercisesOnly` serves the detail-page pop-reload, and only the reactivate paths re-read fully. The hub holds ONE `ExerciseLibraryScreen` instance for its Exercises/Variations tabs (5-child `IndexedStack`; the `panel` param + `didUpdateWidget` flip its internal tab) — the old two-instance layout fetched the whole catalog + timeline twice on hub open. Exercise detail reads the timeline through `TimelineCache`. The workout editor opens via `fetchPlannedSessionById` + `readNormalizedPlannedSession` (in-memory renumbering, zero repair writes on open — the writing variant stays on the save path) and batches lessons with `fetchLessonsForExercises`.
- **The dev flow lab** (`lib/features/dev/lab/`, the "Flow Lab" card on the dev screen) runs the REAL program screens against a sandbox PowerSync database seeded with fake data — `lambda_lab.db` beside the app's own, **never connected**, so nothing it does reaches Supabase. Three moving parts: `swapDatabase` points the global `ps.db` at the sandbox (and hands the app's own back on the way out), `labMode` makes the two REST-first repos (`ProgramRepository`, `ProgramRunRepository`) take local-only remotes, and `lab_seed.dart` builds the world through those same real repositories. It is a top-level route (`/dev/lab`, outside the shell) because the shell's tabs must not be reachable while the app is on the sandbox; the library's push of a program's detail is the one call that switches paths on `labMode`. Opening seeds only what is missing; the header's reset wipes the sandbox and re-seeds. The swap is **holder-counted** (`enter`/`leave` per mounted lab screen, 2026-10-08): overlapping lab screens are real — a pushed second copy disposes first — and before the count, that dispose handed the app's real database back under the lab that stayed open, which is how a review built in the lab reached the user's account.
- **The PR History demo** (`lib/features/dev/view/pr_history_demo_screen.dart`, the "PR History" card on the dev screen, route `/dev/pr-history`) is a fake-data picture of the live session: hard-coded sets in `lib/features/dev/pr_history_fixture.dart` run through the production PR engine, and the exercise card's PRs pill opens the all-time "PR History" sheet (the pill itself quotes only what the demo session added — "+2 PRs", singular "+1 PR" — a gain beside a history, never the all-time total the sheet states; the shared pill's count is session-scoped on every screen, 2026-10-21) — newest first, each PR drawn beside the one prior best it WAS (a single reading: when the exact weight had been handled before, the same-weight prior best — 70 × 8 after 70 × 5 names "70kg × 5" alone, not also 65 × 8; otherwise the best weight at that rep count; unstruck — the label carries the meaning; to the PR's right on the same line), its variation riding the PR's line (bounded in width, never a flex sibling of the outcome's `Expanded` — a flex share it does not use holds WAS/FIRST PR off the row's right edge), when the previous PR landed on the date line ("34 days prior", "Same day") — a gap is a fact about the PR, so filtering never rewrites it. The entries are bare — no rail or dots down the left; each is its date line above its kill line. The sheet stands at a settled 70% of the screen whatever the feed holds — a thin feed or an empty one draws the same room, so the header and filters never move. Filterable to one weight, one rep count and/or one variation (the unvaried line its own answer, "No variation"); the three AND together, the weight and reps fields sharing a row and the variation full width beneath. It stores nothing — no viewmodel, no repository, no DB — and the real session's PRs pill stays inert (2026-10-21).
- **The PR Lab** (`lib/features/dev/pr_lab/`, the "PR Lab" card on the dev screen, route `/dev/pr-lab`) is a **layout sandbox**: a self-contained COPY of the PR History demo's visual stack, so the stage can be rehauled without touching the session, planner, logs or the demo itself (2026-10-21). Every drawn widget has its own `PrLab`-prefixed copy here — `PrLabScreen`, `PrLabExerciseCard`, `PrLabExerciseSelector`, `PrLabSetRow`, `PrLabPageHeader`, `PrLabHeaderIconButton`, `PrLabCardPillButton`, `showPrLabHistorySheet` — with lab-local keys (`pr-lab-*`), and every file carries a LAB COPY banner. The lab imports its copies, never the shared originals, so a production file can never resolve to lab code. Still shared by import (read-only primitives, not layout): styles, `MenuPopover`, `DropdownSelect`, `SwipeActions`, `UndoRedoButtons`, the modals, and the data fixture `pr_history_fixture.dart`. `test/pr_lab_screen_test.dart` covers the copy. Rule: layout experiments land in `pr_lab_*.dart` ONLY — if a change needs a still-shared widget, copy that widget into the lab first (`PrLab` prefix) rather than editing the original.
- **If a release build on device misbehaves but debug works, start from `docs/release_only_crashes.md`** — not from app code. Release/AOT and Debug/JIT are different compilers, so those bugs are usually in the build, not the feature. The `release-crash-triage` skill (`.claude/skills/`) carries the step-by-step checklist.
- **Watch for `+eol` packages** (`grep eol pubspec.lock`). A `+eol` version means a retired mechanism the current toolchain has moved past — that is what broke the 2026-09-30 release build (fixed by `powersync ^1.8.0 → ^2.4.0`, no Dart changes needed).
- **iOS/Xcode 27 build constraints** (pod module verification, deployment-target floor, simulator lipo) are documented in the `ios-toolchain-xcode27` memory.
- **Installing a build on a device via `devicectl` wipes its local database** — flag that to the user before doing it, since unsynced writes are lost.
